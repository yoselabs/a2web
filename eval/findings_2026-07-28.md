## Finding 1 — `other_pages` is mechanically impossible outside the raw tier

> **Twice corrected.** First filed as "corroborates `wikipedia-narrow-ask-indexes`,
> same invariant". Then as "the four index fields defer to each other and no rule
> says one must survive". Both were readings of prompt text. The probe that was
> supposed to rule out a rendering confound found the actual cause instead, and it
> is a code path, not a prompt property. The two earlier diagnoses are recorded
> here because the sequence is the point: prompt-shaped reasoning produced two
> confident, plausible, wrong answers, and one cheap probe settled it.

`listing-answer-always-leaves-an-index` (`arxiv.org/list/cs.CL/recent`) returned
an envelope of `['answer','confidence','operator_hints','tier']` — no index at
all. Probe (`include_links=True`, browser tier): 50 arXiv ids present in
`content_md`, **0 links, 0 headings**, on a page that is nothing but anchors.

```
tier ∈ {browser, jina, zyte, firecrawl, archive} or ANY of the 9 site handlers
  → TierResult.pre_rendered = Rendered(content_md, title, byline, headings)
                                         ↑ dataclass has NO links field
  → _phase_extract copies those four and RETURNS      (fetcher.py:1270-1276)
  → `fc.links = extract_result.links`  NEVER RUNS     (fetcher.py:1318)
  → fc.links == []
  → _build_link_digest: `if not fc.links: return None` (fetcher.py:2317)
  → no '## page links' block reaches the prompt
  → prompt: "If no '## page links' list is present, OMIT other_pages"
```

`other_pages` cannot be emitted on any page not served by the raw tier. Not
"tends not to be" — cannot. Only `raw` runs trafilatura, and trafilatura is the
sole producer of `fc.links`.

**This explains both failing cells with one mechanism.** arXiv came via browser;
`reddit-listing` via zyte. No coincidence required, and no need to guess whether
they were the same defect — they are.

**Scope.** Every browser/handler/archive-served page, i.e. the whole hard-fetch
population — exactly the pages where a caller most needs pointers, since those are
the ones it cannot cheaply re-fetch. ADR-0014's closed-set handle rehydration is
intact and correct throughout; it simply never receives a digest.

**The rendering confound is resolved, and it was real but not causal.** The page
genuinely did render without titles or authors (the model's answer said so
accurately). But titles are not what `other_pages` needs — anchors are, and the
anchors were lost one layer earlier, in a way that has nothing to do with arXiv.

**Not fixed here**, per task 8.3. Whether `Rendered` should carry links, or the
pre-rendered path should run link extraction over the source HTML separately, is
a design call for the change that fixes it.

## What the change DID do — the seam is fixed and provably so

The arXiv envelope grew the fields the seam was dropping:

    before: ['answer','confidence','operator_hints','tier']
    after : ['answer','byline','confidence','operator_hints','tier','title']

and `headings` went 0 → 4 on the same page. Extraction now reaches the

## Why `other_pages` is still impossible — a SECOND gate, same early return

```
_phase_extract, pre-rendered branch          (fetcher.py:1270)
  ├─ fc.links = payload.links                ← FIXED by this change
  └─ RETURN  .............................. before fetcher.py:1320:
        await _run_extraction_escalation(fc, raw_html=raw_html)
             └─ the only producer of json_synth / record_synth candidates

  if not any(c.source in {"json_synth","record_synth"} for c in fc.content_candidates):

```

The same early return drops **two** things. This change fixed the links half.
The candidate half means a pre-rendered page can never satisfy the digest gate,
whatever its links look like.

That gate was flagged in the change's design under Open Questions — *"even on the
raw tier a prose-shaped listing gets no digest; that one looks deliberate"* — and
left alone on the grounds that it was intentional. It is intentional for prose
pages on the raw tier. It is not intentional for every browser-served page, which
is what it amounts to in combination with the early return.

## Correction to the change's claim

`restore-links-on-pre-rendered-tiers` asserted that `other_pages` becomes
reachable on the hard-fetch population. **It does not, yet.** The change is a
necessary precondition — without `fc.links` no digest can be built at all — but
the digest gate makes it insufficient on its own. The proposal should not be
archived as if it delivered that outcome.

Two probes in this session measured the wrong layer and nearly produced wrong

- `r.links == 0` on `FetchResponse` — that is the WIRE field, cleared by the

### The defect this round actually found

`Rendered`'s fields were copied onto the context in **four** places:
`_phase_extract`, `_dispatch_archive`, `_escalate_browser`, `_escalate_paid`.
Round 2 added `links` to exactly one — so its fix was a **no-op on every page
that reached the browser by escalation** (handler wins → gate says
`length_floor` → browser escalates), which is the common path. Measured after
round 2 shipped: `fc.links == 0` on arxiv.

Round 2's guard could not see this. It tested the extraction seam — does the
tier come away with links — and not the install. Both rounds' guards were true
and neither covered the path the corpus case actually takes.

**The pattern across all three rounds is the same and worth naming:** each round
fixed a real defect, verified it at the layer it was written against, and was
measured not to move the outcome — because the next blocker was one layer along.
Fixing an N-copy duplication by patching one copy is round 2; writing a guard
that watches the copy you fixed is round 2's guard. The structural answer landed
this round: one copy, guarded by a rule that fails when a second appears.

### Why the two cells are still unscored — a THIRD blocker, per page

Neither page yields a structured candidate, so the digest gate declines. Direct
probe on `arxiv.org/list/cs.CL/recent`:

    record_mine.extract_records(html)  -> None
    json_in_html.extract_json_payloads -> 0 payloads
    fc.links                           -> 484
    _build_link_digest                 -> None

The gate is behaving exactly as designed — `link-affordances` requires that
non-product/listing genres pay no digest cost, and this page presents no
structured signal to distinguish it. This is a detection gap, not a gate defect,
and it is the reason relaxing `_DIGEST_GATE_SOURCES` remains the wrong lever.

`reddit-listing` reaches the same end state via a different route
(`site_handler:block_page_detected` → `zyte:ok`); `_escalate_paid` already ran
the ladder before this change, so this round could only have helped it via the
links carry.

### The finding that is worth more than the fix

**arXiv's own handler parses the listing and its work is thrown away.**
`handlers/arxiv.py::_fetch_listing` calls `_parse_listing_entries` and builds
`next_links` via `_listing_candidates` — a precise, natively-known index. The
gate then returns `length_floor` on the handler's rendered markdown, the browser
escalates, and the browser's `TierResult` REPLACES the handler's wholesale. The
parsed entries and their links are discarded.

So the page that has been the canonical "no index was left" case has had a
correct index available at tier 0 the entire time, on a path that discards it.
That is a different defect from anything in the last three rounds: not a missing
parse, not a dropped copy, not a starved gate — a losing tier's structured
output being discarded rather than merged.

Recorded, not fixed. It reopens the deferred JSON-API-handler question from both
prior designs with a concrete second example, which is what those designs said
they were waiting for.

### CORRECTION to "the finding that is worth more than the fix"

**That finding is wrong.** It claimed arXiv's handler builds a correct index that
the browser escalation discards. Run, not read:

    ArxivHandler.fetch("https://arxiv.org/list/cs.CL/recent")
      verdict          ok
      next_links       0
      content_md       40 chars   ("# arXiv · cs.CL · recent … ## Papers (0)")

Nothing correct is being discarded. The handler produces almost nothing, which
is WHY the gate returns `length_floor` and the browser escalates. I read
`_parse_listing_entries` and `_listing_candidates`, saw that they exist, and
inferred they work — the same class of mistake as the two wrong-layer probes in
round 2, and the fourth wrong diagnosis in this investigation.

**The actual cause is regex rot.** arXiv's listing HTML uses single-quoted
attributes and a space before the `=`:

    <a href ="/abs/2607.22529" title="Abstract" …>
        arXiv:2607.22529
      </a>
    <div class='list-title mathjax'><span class='descriptor'>Title:</span>

All three handler patterns require double quotes and `href="`, and
`_LIST_ABS_RE` additionally requires the anchor text to sit flush against the
tags. Measured against the live page:

    _LIST_ABS_RE       0 matches      tolerant equivalent   50
    _LIST_TITLE_RE     0 matches
    _LIST_AUTHORS_RE   0 matches

**The structural defect underneath is worth more than the regexes.**
`_fetch_listing` returns `Verdict.ok` with zero parsed entries, and
`_render_listing` renders that as a confident `## Papers (0)`. A parser that
matched nothing reports success. That is the same shape as the empty-vs-wall
invariant — a confident empty produced with no evidence the page was empty —
and it is why this rotted silently for however long it has been rotten. Fixing
the patterns without fixing that guarantees a silent repeat at arXiv's next
markup change.

This also retires the "losing tier's structured output is discarded" backlog
entry: there was no structured output to discard.

H23 **the funnel guard cannot be written by classifying pattern text.** I tried,

- false positives: `(?P<name>` named groups read as markup (`<n`)
- false negatives: `listing_oracle.py:39` — the pattern `rel\s*=\s*["']?...`

### Round 4d — EVOLVE vs PROMOTE, and one sub-thread I could NOT close

H26 **EVOLVE `record-mine` instead of promoting? NO — tested, not assumed.**

The loop warns that growing a sibling when a superset fits is the documented
anti-pattern (resolution 0007), so this had to be checked rather than waved off.

Two reasons EVOLVE does not fit:

1. **Not a container-location problem.** The obvious monotonic evolution — let
   `record-mine` accept an optional container hint, exposing more and removing
   nothing — does not help: handed arXiv's `<dl>` fragment ALONE, with nothing
   else on the page, it still returns `None`. The container was never what was
   missing.
2. **Different axes, so not monotonic.** `record-mine` INFERS generic records
   (`text`, `links`, `heading_text`, `depth`) from an unknown page. A declared
   schema names fields for a KNOWN site. Naming fields exposes more, but
   requiring a selector removes the ability to work on an unknown page — it
   fails the monotonicity test in the removal direction. They are two
   capabilities, not one contract.

consumers in this repo before it is promoted (arxiv, wikipedia, _reddit_html) —
the loop's "second consumer is the first real challenge" is already satisfied.

**NOT CLOSED — why `record-mine` declines arXiv.** Verified twice that it does
(whole page, and given the `<dl>` alone). I could not build a minimal repro: my
synthetic `dl` AND `ul` fixtures both return `None` while the richer
`article.prd` card fixture returns 12, so the detector's thresholds are doing
something I have not characterized. **The earlier note guessing "a `<dl>/<dt>/<dd>`
listing is not the repeated-sibling grid it detects" is therefore UNPROVEN and
should not be cited as a diagnosis.** Reverse-engineering the detector's
heuristics is a separate piece of work; what is established is the symptom, not
the cause.

### Round 4e — H29 closes the design's last hole, and marks its limit

**H29 CONFIRMED for shape A.** A two-level schema (container + child)
separates rot from a genuinely empty page structurally:

    healthy listing        -> OK (2)
    genuinely empty        -> EMPTY_CONFIRMED  (container present, 0 children)
    markup changed (rot)   -> SCHEMA_ROT       (container absent)
    page replaced          -> SCHEMA_ROT       (container absent)

This removes an escape hatch from the draft spec, which said "where a handler
cannot distinguish 'parsed nothing' from 'parsed a genuinely empty page', this
requirement SHALL NOT be applied to it". With a two-level schema it CAN
distinguish, so the guard applies universally rather than conditionally — and
the two outcomes map onto the repo's existing empty-vs-wall doctrine without a
new concept: `EMPTY_CONFIRMED` is a legitimate empty, `SCHEMA_ROT` is non-`ok`
and the cascade continues.

**And it does NOT rescue shape B.** Wikipedia's wikilinks are scattered through
prose; its container is effectively `<body>`, which is always present. Container
presence therefore carries no signal, and a rotted wikilink selector would read
as `EMPTY_CONFIRMED` — the wrong answer, silently. Shape B needs the
expectation/probe mechanism H17 pointed at (assert YIELD against a declared
expectation), not the container split.

So the final design is two mechanisms for two shapes, and each is now justified
by a measurement rather than by symmetry:

| shape | discriminator | mechanism |
|---|---|---|
| A — the parse IS the product (arXiv listing) | container present? | two-level schema, verdict from the split |
| B — auxiliary index over prose (wikipedia) | none available structurally | declared expectation, asserted by the probe |

## Loop closed

Thirteen hypotheses over rounds 4-4e. Remaining unknowns are not
spike-resolvable: reddit's listing parse needs a proxy (403 on www and old),
`block_detector` coverage needs a live wall, and `record-mine`'s arXiv refusal
needs the detector reverse-engineered — deliberately not started.
